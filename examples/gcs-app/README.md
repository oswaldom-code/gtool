# gcs-app — sample application under test

A minimal Go service used to exercise the `gtool` pipeline with Google Cloud
Storage (fake-gcs-server mock → app → Karate tests → cleanup). On startup it
uploads `data/report.json` to `gs://reports/orders/report.json`; the Karate test
reads the object with the launcher's `gcs/ReadObject.feature` and validates its
values.

## Layout

```
gcs-app/
├── component-config.yml          # gtool config: gcs mock, app image, Karate tests
├── data/report.json              # file the app uploads on startup
├── Dockerfile
├── main.go
└── test/component/
    ├── features/report.feature   # reads the object and validates the report
    └── reports/                  # generated by gtool test (git-ignored)
```

Configuration is read from environment variables: `STORAGE_EMULATOR_HOST`,
`BUCKET`, `OBJECT`, `DATA_FILE`, `PORT`. The official Go client targets the
emulator automatically when `STORAGE_EMULATOR_HOST` is set.

## Run it with gtool

```bash
# 1. Build the app image (gtool runs it as a container)
docker build -t gcs-app:latest .

# 2. From this directory, run the full pipeline
gtool test --config component-config.yml
```

`gtool test` starts the GCS emulator (creating the `reports` bucket declared in
`component-config.yml`), starts this app, runs the Karate features in
`test/component/features/`, and tears everything down.

## Networking notes

- **App → emulator:** the app container reaches the host-published emulator
  through `host.docker.internal`, which gtool maps to the host gateway.
- **Tests → emulator:** the Karate launcher runs on the host network. Its
  `gcs/*.feature` helpers expect the emulator on `localhost:9086`, which is why
  the mock is configured with `port: "9086"`.
